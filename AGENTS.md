# Antigravity Project Operating System — V7 Admin Experience Enhanced

This file is read automatically by Antigravity at the start of every session.
It is the single source of authority for how this project is built. If any
other file in this pack appears to conflict with this file, this file wins.

**Do not edit this file, or any file under `docs/`, `agents/`, or `skills/`
during normal feature work.** Those are the project's rules, not its
deliverables. If a rule genuinely needs to change, propose it explicitly,

## HARD RULE: NO CODING BEFORE DISCOVERY

Before writing implementation code:
1. Ask for the project name first.
2. Save the project name in `docs/PROJECT_INTAKE.md`.
3. Inspect the repository if one exists — read it, do not assume its contents.
4. Understand the complete product and all required surfaces.
5. Ask the full discovery questionnaire (`docs/DISCOVERY_QUESTIONNAIRE.md`) and continue follow-up questions until ambiguity is resolved.
6. Produce/finalize PRD, TRD, UI/UX, backend/data model, API contracts, security model, project map, and master plan.
7. Freeze the specification.
8. Create the task graph.
9. Only then implement.

Never ask the user to repeat information already stored in project documentation — read it first.

## ANTI-HALLUCINATION RULES

These apply at all times, not only during verification:

- **Never state that code, a file, a route, or a dependency exists without having actually looked.** Search or open the file first. If you have not checked, say "unverified" rather than asserting it.
- **Never invent an API, library function, config key, or file path.** If you are not certain it exists in this stack/repo, search for it or say you are uncertain.
- **Never claim a test, build, or browser check passed unless you actually ran it in this session and can show the output.** See `docs/EVIDENCE_STANDARDS.md` — this is the binding definition of evidence for every gate below.
- **When a requirement is ambiguous, ask** (see `skills/requirements-question-loop/SKILL.md`) rather than silently choosing an interpretation.
- **Distinguish assumptions from facts out loud.** If you must proceed on an assumption because the user is unavailable, label it as an assumption and record it in `docs/DECISION_LOG.md` so it can be corrected later.
- **A confident tone is not evidence.** Prefer "I verified X by running Y and observed Z" over "X works correctly."

## CLEAN CODE / NO WASTE

Before creating code, search for an existing implementation.

Rules:
- Never duplicate business logic.
- Never duplicate API logic.
- Never duplicate UI behavior unnecessarily.
- Never duplicate database concepts.
- Reuse one implementation when behavior is genuinely shared.
- Do not force abstractions when behavior is unrelated.
- Remove safely unused/dead code (see `skills/dead-code-cleanup/SKILL.md`).
- No generic junk files such as `utils2`, `helpers-new`, `misc`, or catch-all folders.
- Keep folder structure understandable to a normal developer.
- Refactor before adding a second implementation.
- Do not perform unrelated cosmetic refactors.

## API READINESS

Required APIs are not deferred "for later".
An API is only ready when:
- request/response contract exists,
- validation exists,
- auth/RBAC is defined,
- errors are predictable,
- frontend integration works (actually exercised, not assumed),
- realistic test data exists,
- tests pass (with output as evidence),
- browser verification succeeds where applicable,
- documentation explains how a developer modifies it.

Prefer simple, explicit, typed contracts over clever abstractions.

## ROUTES AND LINKS

Every route, link, button, form submission, redirect and deep link must have a traceable purpose and valid destination.

Before completion run the route/link audit (`skills/route-link-audit/SKILL.md`). No placeholder `#`, fake URLs, dead navigation, or broken internal links.

## PREMIUM PUBLIC WEBSITE EXPERIENCE — REQUIRED FOR ALL CUSTOMER-FACING WEB UI

For public websites, the default target is a bespoke, editorial, premium interface — not a template-like collection of gradients, cards, hero banners, or generic AI UI patterns.

Before implementation, consult:
- `docs/PREMIUM_WEBSITE_DESIGN_SYSTEM.md`
- `docs/ERROR_RESILIENCE.md`
- `docs/PERFORMANCE_LIGHTWEIGHT_SCALABILITY.md`
- `docs/SEO_INFORMATION_ARCHITECTURE.md`
- `docs/ACCESSIBILITY_MEDIA.md`
- `docs/NETWORK_RESILIENCE.md`
- `docs/IMAGE_OPTIMIZATION.md`

Hard design rules:
- Do not use gradient backgrounds as the primary visual treatment unless the product brief explicitly requires them.
- Do not build every section as a rounded card.
- Do not produce a static page where scroll can naturally communicate hierarchy, progression, depth, or narrative.
- Prefer art-directed composition: asymmetric grids, editorial typography, layered media, whitespace, controlled overlap, section transitions, sticky moments, progressive reveals, and meaningful micro-interactions.
- Motion must communicate structure or state. Never add animation only to make the page look "AI generated".
- The site must remain premium with motion disabled and on low-power/mobile devices.
- Every visual decision must survive responsive, accessibility, reduced-motion, and slow-network conditions.

## WEB QUALITY GATES — REQUIRED FOR EVERY PUBLIC WEBSITE

Before a public website is considered complete, verify all applicable areas:
- route and link integrity;
- 404/403/429/500/error-boundary states;
- offline, timeout, retry, and slow-network behavior;
- `robots.txt`, sitemap, canonical URLs, metadata, Open Graph/Twitter cards, structured data;
- heading hierarchy and semantic landmarks;
- descriptive image alt text and decorative-image handling;
- image dimensions, responsive formats, lazy loading, priority strategy, and layout-shift prevention;
- JavaScript bundle and dependency budget;
- Core Web Vitals / real-user performance where measurable;
- keyboard navigation, focus visibility, contrast, labels, and reduced motion;
- responsive behavior at mobile, tablet, desktop, wide desktop;
- browser compatibility for the declared support matrix;
- security headers and safe error messages;
- analytics/consent behavior where applicable;
- production build and clean-console checks.

Never mark a website complete merely because the happy-path homepage renders.

## DEPENDENCY / PRE-BUILT LIBRARY POLICY

Use mature pre-built libraries when they materially improve reliability, accessibility, or development speed. Do not rebuild solved infrastructure.

Before adding a library:
1. Identify the exact problem it solves.
2. Check maintenance/activity, license, bundle impact, transitive dependencies, and compatibility.
3. Search the existing codebase for an equivalent implementation.
4. Prefer one focused library over several overlapping packages.
5. Load browser-heavy libraries only where required.
6. Avoid libraries that force a visual style inconsistent with the bespoke design system.
7. Record important dependency decisions in `docs/DEPENDENCY_READINESS.md`.

For animation, image, UI, icons, forms, validation, SEO, analytics, and utilities, choose the smallest reliable solution that satisfies the requirement.

## ERROR / FAILURE UX POLICY

Every user-facing asynchronous or navigational action must have a defined state:
`idle → loading → success | empty | validation-error | permission-error | not-found | rate-limited | timeout | network-error | server-error`.

Each recoverable failure must provide:
- a clear human-readable explanation;
- a useful next action;
- a retry path where retry is meaningful;
- preserved user input where safe;
- no raw stack traces, SQL errors, provider secrets, or internal implementation details.

## PERFORMANCE POLICY

The project must define budgets before implementation:
- initial HTML response;
- critical CSS;
- JavaScript shipped on first view;
- third-party scripts;
- image payload;
- font payload;
- total above-the-fold transfer;
- route-level loading time;
- animation cost;
- DOM complexity where relevant.

Performance is a product requirement, not a post-launch optimization task.

## SEO POLICY

SEO must be modeled as information architecture, not a collection of meta tags.
Every indexable route must have:
- one intentional canonical URL;
- one primary search intent;
- one clear H1;
- logical H2/H3 hierarchy;
- unique title and description where appropriate;
- index/follow decision;
- internal-link purpose;
- structured-data eligibility decision;
- image alt strategy;
- sitemap/robots inclusion decision.

## ACCESSIBILITY POLICY

All interactive public UI must be keyboard operable, semantically structured, screen-reader understandable, visibly focusable, and usable with reduced motion. Images must have intentional alt behavior. Color must never be the only carrier of meaning.

## SCROLL / MOTION POLICY

Use scroll-driven behavior selectively:
- reveal content when it improves sequencing;
- pin only when the pinned content has a clear narrative purpose;
- use parallax only when it remains performant;
- prefer transform/opacity over layout-triggering animation;
- respect `prefers-reduced-motion`;
- provide an equivalent static experience;
- never trap scrolling or hijack browser navigation.



Before building or significantly redesigning an admin panel, internal tool, operations workspace, moderation queue, fleet workspace, booking workspace, verification queue, CMS workspace, or staff/RBAC workspace:

1. Consult `agents/admin-experience-architect.md`.
2. Apply `skills/admin-experience-first/SKILL.md`.
3. Read `docs/design/ADMIN_EXPERIENCE_SYSTEM.md`.
4. Define the administrator's primary job, information hierarchy, entities/relationships, action hierarchy, workspace pattern, interaction placement, operational states, attention model, and responsive strategy before implementation.

**The anti-pattern to prevent:** never interpret an admin request as simply "sidebar + tabs + cards + table + modal." Design the operational workflow first.

## DESIGN SYSTEM — REQUIRED FOR ALL UI WORK

Before building any UI component, page, screen, admin panel, CMS view, iOS
screen, or Android screen:

1. Confirm `docs/design/DESIGN_TOKENS.md` is filled in with real values from
   the homepage. If it is empty, run `agents/design-system-extractor.md` first.
2. Apply `skills/design-system-first/SKILL.md` — use tokens, not hardcoded values.
3. After building, apply `agents/design-qa-engineer.md` checklist before marking done.

**The 5 design issues that indicate a token was not used:**
- Borders of two sections touching with no breathing room → use `space-16` section padding
- Text is pure black (`#000`) → use `text-default` from tokens
- Icon overlapping or touching its label → use `gap-2` (8px) between icon and text
- Icon too large for its context → use `icon-sm`/`icon-md`/`icon-lg` from tokens
- Admin panel colors differ from homepage → use same tokens as web

**Additional design skills (auto-triggered by context, or open directly):**
- `skills/spacing-layout-check/SKILL.md` — when layout feels cramped
- `skills/typography-check/SKILL.md` — when text looks wrong
- `skills/icon-usage-check/SKILL.md` — when icons look off
- `skills/cross-surface-consistency/SKILL.md` — when building admin/CMS/app

**For mobile apps:** also run `agents/mobile-app-orchestrator.md` and update
`docs/MOBILE_FEATURE_MATRIX.md` and `docs/memory/MOBILE_STATE.md`.

## QUALITY AND SAFETY

Do not:
- fake verification,
- hide TODOs,
- silently change requirements,
- delete failing tests to make a build green,
- use mocks as accidental production paths,
- hardcode business-critical data,
- claim completion when blocked.

When a required dependency is unavailable, either implement it now or explicitly mark the task BLOCKED with the reason and recovery path in `docs/TASK_REGISTRY.md`.

Use type safety, dependency governance, security review, failure-path testing, observability, environment safety, and regression checks.

## SCOPE

Optimize for the finished product, not merely the current prompt:
- complete everything required for the requested outcome;
- do not build unrelated features;
- do not expand scope without recording a change request (`skills/change-management/SKILL.md`).

## FINAL GATE

Before COMPLETE, every item below must have real evidence per `docs/EVIDENCE_STANDARDS.md`, not just a checked box:
1. Requirements traceability passes (`docs/REQUIREMENTS_TRACEABILITY.md`).
2. Feature completion matrix passes (`docs/FEATURE_COMPLETION_MATRIX.md`).
3. Route/link audit passes (`docs/ROUTE_LINK_REGISTRY.md`).
4. API contract and integration audit passes.
5. Code reuse/dead-code audit passes.
6. Security gate passes (`docs/SECURITY_THREAT_MODEL.md`).
7. Tests pass — with actual output.
8. Browser/E2E verification passes where applicable — with actual observed steps.
9. Design QA passes (`agents/design-qa-engineer.md`) — no CRITICAL or HIGH design failures.
10. Documentation/state are updated.
10. Completion auditor (`agents/completion-auditor.md`) signs off, and does so adversarially — its job is to find reasons the work is NOT done, not to confirm it is.

A perfect result cannot be guaranteed by process, but incomplete or unverified work must never be represented as complete.
